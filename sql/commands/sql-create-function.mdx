---
title: "CREATE FUNCTION"
description: "The `CREATE FUNCTION` command can be used to create [user-defined functions](/sql/udfs/user-defined-functions) (UDFs)."
---

There are three ways to create UDFs in RisingWave: UDFs as external functions, embedded UDFs and SQL UDFs. `CREATE FUNCTION` can be used for them with different syntax.

## UDFs as external functions

You can define your own functions (including table functions) by some programming languages, like Python and Java, and call these functions in RisingWave.

The `CREATE FUNCTION` command is used to declare these UDFs. After that, you can use them in SQL queries like any built-in functions.

### Syntax

```sql
CREATE FUNCTION [ IF NOT EXISTS ] function_name ( argument_type [, ...] )
    [ RETURNS return_type | RETURNS TABLE ( column_name column_type [, ...] ) ]
    [ LANGUAGE language_name ]
    [ IMMUTABLE | STABLE | VOLATILE ]
    AS function_name_defined_in_server
    USING LINK 'udf_server_address'
    [ WITH ( function_option = boolean [, ...] ) ];
```

<Note>
Added in v2.3.0: Support `IF NOT EXISTS`.
</Note>

### Parameters

| Parameter or clause                          | Description                                                                                                                                                                                                                                                                                                                          |
| :------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| _function\_name_                             | The name of the UDF that you want to declare in RisingWave.                                                                                                                                                                                                                                                                          |
| _argument\_type_                             | The data type of the input parameter(s) that the UDF expects to receive.                                                                                                                                                                                                                                                             |
| **RETURNS** _return\_type_                   | Use this if the function returns a single value (i.e., scalar). It specifies the data type of the return value from the UDF.The struct type, which can contain multiple values, is supported. But the field names must be consistent between the programming language and SQL definitions, or it will be considered a type mismatch. |
| **RETURNS TABLE**                            | Use this if the function is a table-valued function (TVF). It specifies the structure of the table that the UDF returns.                                                                                                                                                                                                             |
| **LANGUAGE**                                 | **Optional**. Specifies the programming language used to implement the UDF.  Currently, Python, Java,Rust, and JavaScript are supported.                                                                                                                                                                                                 |
| **IMMUTABLE \| STABLE \| VOLATILE**          | **Optional**. Specifies a volatility declaration. Currently, only `IMMUTABLE` has an effect, and only as a prerequisite check when `skip_materializing_eval_result` is `true`. `STABLE` and `VOLATILE` are accepted but have no effect.                                                                                                   |
| **AS** _function\_name\_defined\_in\_server_ | Specifies the function name defined in the UDF server.                                                                                                                                                                                                                                                                               |
| **USING LINK** '_udf\_server\_address_'      | Specifies the UDF server address. If you are running RisingWave in your local environment, the address is http://localhost: \<port>  If you are running RisingWave using Docker, the address is http://host.docker.internal: \<port>/                                                                                                    |
| **WITH**                                     | **Optional**. Specifies UDF execution options. For result materialization options, see [Skip result materialization for a UDF](#skip-result-materialization-for-a-udf).                                                                                                                                                                  |

### Examples

Use `CREATE FUNCTION` to declare an external UDF defined by Python or Java. For more details, see [Use UDFs in Python](/sql/udfs/use-udfs-in-python) or [Use UDFs in Java](/sql/udfs/use-udfs-in-java).

```sql
CREATE FUNCTION gcd(int, int) RETURNS int
AS gcd
USING LINK 'http://localhost:8815'; -- If you are running RisingWave using Docker, replace the address with 'http://host.docker.internal:8815'.
```

## Embedded UDFs

Embedded UDFs are functions that run in the language runtime embedded in RisingWave computation nodes. The `CREATE FUNCTION` command is used to create these UDFs.

Here are some examples of embedded UDFs, along with links to specific guides on creating them with different languages.

```sql Embedded UDFs
-- Embedded Python UDF
CREATE FUNCTION gcd(a int, b int) RETURNS int LANGUAGE python AS $$
def gcd(a, b):
    while b != 0:
        a, b = b, a % b
    return a
$$;
```

For more details, see [Embedded Python UDFs](/sql/udfs/embedded-python-udfs).

```sql Embedded UDFs
-- Embedded JavaScript UDF
CREATE FUNCTION gcd(a int, b int) RETURNS int LANGUAGE javascript AS $$
    while (b != 0) {
        let t = b;
        b = a % b;
        a = t;
    }
    return a;
$$;
```

For more details, see [Use UDFs in JavaScript](/sql/udfs/use-udfs-in-javascript).

```sql Embedded UDFs
-- Embedded Rust UDF
CREATE FUNCTION gcd(int, int) RETURNS int LANGUAGE rust AS $$
    fn gcd(mut a: i32, mut b: i32) -> i32 {
        while b != 0 {
            let t = b;
            b = a % b;
            a = t;
        }
        a
    }
$$;
```

For more details, see [Use UDFs in Rust](/sql/udfs/use-udfs-in-rust).

## Skip result materialization for a UDF

<Note>
Added in v3.2.0.
</Note>

By default, RisingWave treats calls to external and embedded UDFs as impure for streaming planning. Where result materialization is required on a retract or upsert input, RisingWave stores the complete projected expression so that delete and update-delete records can reuse the previously evaluated result.

For a deterministic, side-effect-free UDF, set `skip_materializing_eval_result` to `true` to prevent that UDF from making an otherwise pure expression require result materialization. The option defaults to `false`.

<Note>
This option applies only to external and embedded UDFs. A `LANGUAGE sql` definition currently accepts but ignores `skip_materializing_eval_result`, so specifying it for a SQL UDF does not change result-materialization planning.
</Note>

```sql Skip result materialization for a deterministic UDF
CREATE FUNCTION identity_without_stored_result(v int)
RETURNS int
LANGUAGE javascript
IMMUTABLE
AS $$
export function identity_without_stored_result(v) {
    return v;
}
$$
WITH (
    skip_materializing_eval_result = true,
    always_retry_on_network_error = true
);
```

RisingWave rejects `skip_materializing_eval_result = true` unless both of these requirements are met:

- Declare the function `IMMUTABLE`.
- Set `always_retry_on_network_error = true`. For external scalar UDF calls, this option retries supported remote transport errors indefinitely. A persistent network failure can therefore stall streaming progress.

<Warning>
Enable this option only when repeated evaluations with the same input always return the same result and have no side effects. RisingWave checks for the `IMMUTABLE` clause but cannot verify the UDF implementation. Without a stored result, RisingWave can reevaluate the UDF for delete and update-delete records. A different result can cause inconsistent retractions or an execution panic.
</Warning>

If an argument contains an unmarked UDF or another impure expression, RisingWave still materializes the complete top-level projected expression. The option does not selectively materialize nested subexpressions.

### Interaction with the session-level override

Keep [`streaming_unsafe_allow_unmaterialized_impure_expr`](/operate/view-configure-runtime-parameters) set to `false` to use the scoped per-function behavior. In this mode, only UDFs marked with `skip_materializing_eval_result = true` stop making an otherwise pure expression require materialization; other impure expressions retain the default protection.

If `streaming_unsafe_allow_unmaterialized_impure_expr` is `true` when RisingWave plans a streaming job, RisingWave skips planner-inserted result materialization for all impure expressions in that job, regardless of each UDF's `skip_materializing_eval_result` setting. This session-level override is broader and carries the same risk of inconsistent results or execution panics.

## SQL UDFs

SQL UDFs in RisingWave are designed to expand directly into expressions at the frontend, resulting in minimal performance difference compared to manually calling multiple functions.

The `CREATE FUNCTION` command is used to define SQL UDFs. You can read our guide on [SQL UDFs](/sql/udfs/sql-udfs) for more details.

```sql Syntax of SQL UDFs
CREATE FUNCTION [ IF NOT EXISTS ] function_name ( argument_type [, ...] )
    RETURNS return_type
    LANGUAGE sql
    { AS as_definition | RETURN return_definition };
```

<Note>
Added in v2.3.0: Support `IF NOT EXISTS`.
</Note>
