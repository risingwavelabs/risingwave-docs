---
title: "Benchmark object storage with risectl"
description: "Use risectl to measure S3-compatible object storage operations and compactor-style reads without connecting to a RisingWave cluster."
---

The `risectl bench object-store` command measures S3-compatible object storage through the same object store client that RisingWave uses. It runs locally in the `risectl` process and does not require a running RisingWave cluster, a Meta connection, or Kubernetes resources.

The benchmark supports Amazon S3 and S3-compatible services such as MinIO. It performs a functional preflight before preparing the benchmark data.

<Warning>
The benchmark creates, reads, lists, and deletes objects and can generate significant storage and network traffic. Use a dedicated test bucket when possible, and avoid running it against storage that serves a production workload.
</Warning>

## Prerequisites

Before running the benchmark, prepare:

- `risectl` and access to the object store from the host where you run it.
- An `s3://` or `minio://` store URL. Pass it with `--store`, or set `RW_HUMMOCK_URL`.
- Credentials that can upload, read, list, and delete objects in the target bucket. Configure credentials, the endpoint, TLS, and related settings as you do for RisingWave.

You can optionally pass an existing `risingwave.toml` with `--config-path`. The command reads the `[storage.object_store]` settings from that file. It does not connect to the cluster described by the configuration.

## Run a benchmark

The following example runs the basic profile and saves the JSON report to `report.json`:

```bash
risectl bench object-store \
  --store s3://benchmark-bucket \
  --config-path /etc/risingwave.toml \
  --profile basic \
  --objects 16 \
  --object-size 64MiB \
  --concurrency 8 \
  --output report.json
```

If you use the `risingwave` binary instead of the standalone `risectl` binary, replace `risectl` with `./risingwave ctl`.

The command supports these profiles:

| Profile | Workload |
| --- | --- |
| `basic` | Measures complete streaming uploads, random ranged GETs, small block GETs, complete prefix listings, and batched deletion of existing objects. Each measured operation phase schedules work for up to 30 seconds or 10,000 attempts by default. |
| `compactor` | Compares continuous reads, intermittent reads from an open response, and separate short ranged GETs. It also compares a fast-reader cohort alone and with continuous or intermittent readers. |
| `all` | Runs both profiles with shared data preparation and cleanup. This is the default. |

Use `--basic-duration-ms 0` to make the basic profile use fixed operation counts instead of timed phases.

## Configure the workload

Common options include:

| Option | Description |
| --- | --- |
| `--objects` | Number of large objects. The default is `16`. |
| `--object-size` | Size of each large object. The default is `64MiB`. |
| `--concurrency` | Number of concurrent workers. The default is `8`. |
| `--basic-duration-ms` | Wall-clock scheduling budget for each basic phase. The default is `30000`; use `0` for fixed-count mode. |
| `--basic-max-operations` | Maximum logical attempts per basic phase, including failures. The default is `10000`. |
| `--pause-ms` | Base pause between eligible chunks in non-continuous compactor reads. The default is `10000`. |
| `--pause-every-chunks` | Pause after this many nonempty chunks. The default is `1`. |
| `--max-pauses` | Maximum pauses per logical read. By default, the number is unlimited; `0` disables pauses. |
| `--max-runtime-secs` | Cooperative deadline for the entire command. The default is `1800`. |
| `--parameters` | JSON file containing benchmark parameters. Explicit CLI options override the file. |

Run `risectl bench object-store --help` for the complete option list. For example, you can configure range and block sizes, metadata object counts, interference duration, jitter, and the S3 client backend.

## Collect results and traces

The command writes a human-readable summary to standard error and one JSON report to standard output. If you specify `--output`, it also saves the JSON report atomically at that path. The report includes effective settings, phase throughput and operation counts, successful and failed latency distributions, stop reasons, retry observations, and cleanup results.

For compactor-style read diagnostics, add `--trace-output`:

```bash
risectl bench object-store \
  --store s3://benchmark-bucket \
  --profile compactor \
  --objects 16 \
  --object-size 64MiB \
  --concurrency 8 \
  --pause-ms 1000 \
  --max-pauses 1 \
  --output report.json \
  --trace-output reads.jsonl
```

The trace records compactor and interference read spans as JSON Lines. The destination file must not already exist, its parent directory must exist, and it must differ from `--output`. Tracing adds CPU and scheduling overhead, so check `read_trace.complete`, `read_trace.summary.records_written`, and `read_trace.summary.records_dropped` in the report before relying on the trace.

## Interpret the results

Keep these measurement boundaries in mind:

- Results describe client-observed logical operations, not physical HTTP requests or SDK retry counts. Complete upload latency is not individual multipart upload latency, and a complete listing can include metadata requests.
- Stream-poll timing can include buffered data. Cache state and server backpressure are not verified, and intentional pauses are included in end-to-end latency.
- Latency quantiles are descriptive. A small sample does not establish stable tail latency.
- The command does not apply automatic performance thresholds. Compare runs made with the same topology, object store configuration, dataset, and workload settings.

## Clean up benchmark data

By default, each run uses a unique `risectl-bench/<run-id>/` prefix and attempts to delete the known objects it created. The JSON report records the prefix and cleanup status.

Use `--keep-data` to retain the objects for inspection. A later `compactor` run can read retained large objects with `--reuse-prefix <prefix>`. If the process terminates abruptly or a multipart upload cannot be aborted, you might need to remove leftover data using the object store's lifecycle or administration tools.

For guidance on diagnosing storage-related cluster bottlenecks, see [Object store issues](/performance/specific-bottlenecks#object-store-issues).
